# Yandex Maps Reviews Parser

Веб-приложение для получения информации об организациях и отзывах из Yandex Maps.

Проект состоит из Laravel API, Vue 3 frontend и отдельного Node.js-парсера, использующего Puppeteer для работы с динамической страницей Yandex Maps.

---

## Возможности

- авторизация пользователей;
- добавление организации по ссылке на Yandex Maps;
- асинхронный запуск парсинга через Laravel Queue;
- получение информации об организации;
- получение среднего рейтинга;
- получение количества оценок;
- получение количества отзывов;
- получение отзывов организации;
- загрузка до 600 отзывов одной организации;
- динамическая загрузка отзывов со страницы Yandex Maps;
- пагинация отзывов по 50 элементов;
- отображение прогресса выполнения парсинга;
- повторные попытки выполнения задачи при ошибке;
- обработка ошибок загрузки и изменения структуры страницы;
- предотвращение повторного сохранения одинаковых отзывов;
- просмотр списка обработанных организаций.

# Описание подхода к парсингу и обходу защиты

- Ответы на п.1-п.5 "Дополнительные требования" представлены ниже более детально раскрывая порядок и процесс разработки.

* На практике столкнулась с вопросом "Действительно ли нет API у Яндекса", выяснив что его действительно не существует начала думать что можно сделать.
* Вывела получение данных через браузерную автоматизацю Puppeteer + Chromium, в процессе выяснила что Яндекс достаточно интересно поставил защиту от подобного подхода именно на Яндекс.карты, добавив требования по "человечности браузера" соответственно userAgent.
* **Как и что работает на практике:** Laravel отвечает за API, авторизацию, очередь и сохранение. Парсер для взаимодействия с Яндекс картами вынесен отдельно. Парсер принимает ссылку на организацию в обоих вариантах (прямо из карточки и из поисковой строки, ссылки одинаковы и зашито в них одно и то же), после открывает страницу в Chromium, постепенно с небольшими человеческими задержками листая отзывы в ожидании подгрузки новой пачки отзывов. Количество полученных отзывов контролируется в соответствии с тз (максимум 600). При условии что отзывов меньше 600, парсер получает их все, если же больше 600, то только релевантные 600. Полученные данные проходят валидацию перед передачей в Laravel, в результате возвращается понятный JSON.
* **Почему именно headless-браузер?** Преимущества и недостатки, более масштабное обоснование представлено в п.2 "Дополнительные требования". Для задачи рассматривалось оба предложенных варианта headless-браузер и json запросы. На нулевом этапе, анализе обоих подходов, выяснилось что отзывы подгружаются динамически и в первом внутреннем запросе выдаётся только 50 отзывов, внутренние эндпоинты, параметры и токены могли бы легко поменяться, что соответственно не подходило так как нарушало бы устойчивость к сменам, выдавая даже если и осознанную ошибку, то точно заставляло бы каждый раз по новой анализировать сетевое взаимодействие и запросы. Headless-браузер оказался оптимальным вариантом с моей точки зрения, позволяя достаточно быстро и просто достать актуальную DOM структуру, выборочно брать информацию из определённых классов и взаимодействовать со страницей как реальный пользователь.

# Дополнительные требования

## 1. Устойчивость к смене разметки

Yandex Maps использует динамическую страницу, DOM-структура и отдельные элементы которой могут изменяться.
Чтобы изменение структуры страницы не приводило к сохранению пустых или некорректных данных, parser выполняет валидацию результата перед его передачей в Laravel.

Проверяется:

- доступность страницы;
- наличие данных организации;
- наличие идентификатора организации;
- наличие раздела отзывов;
- наличие счётчиков;
- корректность рейтинга;
- корректность количества отзывов;
- наличие обязательных полей отзыва;
- корректность оценки;
- корректность даты публикации;
- соответствие количества загруженных отзывов ожидаемому количеству.

Если обязательный элемент отсутствует или полученные данные имеют некорректный формат, parser завершает работу с ошибкой.

Laravel дополнительно проверяет:

- успешность завершения Node.js-процесса;
- наличие ответа;
- корректность JSON;
- наличие данных организации;
- наличие массива отзывов;
- корректность отдельных отзывов.

Пустой или некорректный результат не считается успешным парсингом.
Ошибка передаётся в Queue Job, записывается в Laravel log, а соответствующий `ParsingRequest` переводится в статус `failed`.

Таким образом, изменение разметки должно приводить к явной ошибке, а не к молчаливому сохранению некорректных данных.

## 2. Обоснование подхода к парсингу

Для получения данных используется headless-браузер **Puppeteer + Chromium**.

Рассматривались два основных подхода:

1. разбор внутренних JSON-запросов Yandex Maps;
2. использование headless-браузера.

### Внутренние JSON-запросы

Преимущества:

- высокая скорость;
- меньшее потребление ресурсов;
- отсутствие необходимости полностью загружать страницу.

Недостатки:

- зависимость от внутренних endpoint'ов;
- возможное изменение формата запросов;
- возможное изменение параметров и токенов;
- необходимость дополнительно анализировать сетевое взаимодействие страницы.

### Headless-браузер

Преимущества:

- работа с реальной страницей;
- поддержка JavaScript;
- возможность взаимодействовать с динамическими элементами;
- возможность прокручивать контейнер отзывов;
- отсутствие прямой зависимости от внутренних API-запросов;
- возможность контролировать факт появления новых отзывов.

Недостатки:

- более высокое потребление CPU и RAM;
- необходимость запуска Chromium;
- меньшая скорость по сравнению с прямыми HTTP-запросами;
- зависимость от DOM-селекторов;
- необходимость обновления parser при существенном изменении интерфейса.

Для текущего проекта выбран Puppeteer, поскольку отзывы загружаются динамически при взаимодействии со страницей Yandex Maps.

## 3. Масштаб и фоновая обработка

Парсинг выполняется асинхронно через **Laravel Queue**, поэтому длительная обработка организаций и большого количества отзывов не блокирует HTTP-запрос. Для каждого запуска создаётся `ParsingRequest`, а задача
ередаётся в `ParseOrganizationJob`. Состояние и прогресс (`pending`, `processing`, `completed`, `failed`) сохраняются в БД и отслеживаются frontend через API. При временном сбое задача автоматически повторяется до
3 раз с задержкой 25 секунд. Такой подход позволяет масштабировать обработку большого количества организаций
за счёт увеличения числа Queue Workers.

## 4. Анти-бан на объёме

При регулярном парсинге большого количества карточек нагрузка ограничивается за счёт очереди и контролируемого количества одновременно выполняемых задач. В процессе работы Puppeteer использует реалистичный User-Agent, ожидает загрузку необходимых элементов и выполняет постепенную прокрутку контейнера отзывов с контролем прогресса, не допуская бесконечных повторных действий при отсутствии новых данных. На уровне Laravel Queue настроены повторные попытки с задержкой (`3` попытки, `25` секунд между ними), поэтому временные ошибки не приводят к немедленным повторным запросам. Если парсер не может корректно получить данные, результат не сохраняется: ошибка логируется, а после исчерпания попыток `ParsingRequest` переводится в статус `failed`. При дальнейшем увеличении нагрузки дополнительно может быть использован throttling количества параллельных воркеров, пул прокси и User-Agent, а также отдельное определение признаков блокировки с последующим увеличением backoff.

## 5. Идемпотентность и история изменений

При повторном парсинге организации дубли не создаются: организация определяется по `external_id` Yandex Maps и сохраняется через `updateOrCreate()`, а для отзывов используется `firstOrCreate()` по комбинации `organization_id`, `author`, `published_at`, `text` и `rating`. История запусков уже хранится в `ParsingRequest`, а для полноценного отслеживания изменений между парсингами можно добавить таблицу `organization_snapshots`, в которой при каждом успешном парсинге сохранять текущие `name`, `rating`, `ratings_count` и `reviews_count`, что позволит сравнивать состояние организации по принципу «было → стало».

## Что бы было сделано при наличии большего времени

При наличии дополнительного времени я бы добавила полноценную историю изменений через snapshots, отдельный механизм определения блокировки, throttling Queue Workers, управление пулом proxy, мониторинг очередей,дополнительные интеграционные/E2E-тесты и расширить пользовательский интерфейс.
